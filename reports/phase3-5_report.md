### 2-1. 발음 사전: Kokoro G2P(misaki) 음소 출력 비교 (run 12·14, 같은 결과)

음소 문자열은 G2P의 출력이지 신경망이 실제로 내는 소리가 아니다. 의도와 다르다는 증거로는 충분하지만 맞다는 증거는 아니다.
`A`=/eɪ/, `W`=/aʊ/, `O`=/oʊ/ (misaki 표기).

| 단어 (의도) | 철자 그대로 | 지시서식 치환 | 판정 |
|---|---|---|---|
| Ekam (EH-kum) | `ˈɛkæm` | `ehkum` -> `ˈAkəm` | 치환이 **어긋남**(에이). `ekum` -> `ˈɛkəm`이 의도와 일치 |
| Dve (dveh) | `dˌivˌiˈi` (글자 읽기) | `dveh`/`dvay` -> `dˈivˈA` | 철자 치환은 d 뒤에 모음 `i`가 끼어듦. `dway` -> `dwˈA`는 v가 w로 바뀜. 음소 표기 `[Dve](/dvˈA/)`만 `dvˈA` 유지 |
| Trini (TREE-nee) | `tɹˈɪni` | `treenee` -> `tɹˈini` | 치환이 나음 |
| Chatvari | `ʧætvˈɑɹɹi` | `chahtvahree` -> `ʧˈɑtvɑɹˌi` | 치환이 나음 |
| Pancha / Shat / Sapta | `æ`계열 | `ʌ`계열 | 치환이 의도(ʌ)에 가까움 |
| Ashtau (ASH-tow) | `ˈæʃtW` (아우) | `ashtow` -> `ˈæʃtO` (오우) | 철자 그대로가 **맞음**, 치환이 어긋남 |
| Nava | `nˈɑvə` | `nahvah` -> `nˈɑvə` | 동일 |

이에 따라 `examples/surya_a/script.yaml`의 항목을 `Ekam: "EK-um"`, `Dve: "/dvˈA/"`, `Ashtau: "ASH-tau"`로 바꿨다(대본 문구는 그대로).
`Dve`의 음소 표기가 신경망 음성에서 자연스러운지는 모른다 - 첫 청취 항목이다.

run 16(수정 후)에서 확인: `Dve.` -> `[Dve](/dvˈA/).`가 실제 Kokoro를 거쳐 합성되고 단어 시각(`Dve[0.00-0.52]`)도 나오며 fit은 전 항목 ok. 음소 표기로 바꾸자 `Dve` 길이가 0.64초에서 0.52초로 달라졌다(소리가 바뀐 것은 확실, 좋아졌는지는 청취 필요). 음량 수치는 재현됨(마스터 -19.6 LUFS, BGM 없이 -15.5).

### 2-2. 목표 -14 LUFS를 실제 Kokoro 음성에서 못 맞추는 원인 (Q5의 답)

합성 BGM(사인 화음)과 af_heart로 만든 94.5초 가이드. 러너 측정이며 실제 곡이 아니다.

| 측정 | 값 |
|---|---|
| 내레이션 스템 | -25.7 LUFS / 피크 -7.2 dBTP / PLR 18.5 dB |
| premix(내레이션+BGM+큐) | -29.5 LUFS / -7.1 dBTP / PLR 22.4 dB |
| 마스터 결과(이득 +10.1 dB, 리미터 예산 4 dB 소진) | **-19.5 LUFS** / -1.4 dBTP |
| 내레이션+큐만(BGM 없음) 마스터 | -15.3 LUFS (목표 -14에 1.3 dB 부족) |
| 내레이션에 acompressor 2:1 / 3:1 / 4:1 후 마스터 | -20.2 / -21.1 / -23.0 LUFS (**악화**) |

- 스템을 다시 합산한 재구성이 premix(-29.5)와 일치해 측정 자체는 믿을 수 있다.
- 목표를 맞추려면 PLR이 약 17 dB(= 목표 -14와 한도 -1 사이 13 dB + 리미터 예산 4 dB) 이하여야 하는데 내레이션 PLR은 18.5 dB로 약 1.5 dB 모자란다. BGM 없이도 -15.3에서 멈추는 이유다.
- BGM을 얹으면 4.2 dB가 더 떨어진다(-15.3 -> -19.5). 가장 그럴듯한 설명은 BS.1770 게이팅이다: BGM이 내레이션보다 14.5 dB 낮게 깔려 있어 BGM만 있는 블록이 상대 게이트(-10 LU) 경계에 걸려 평균을 끌어내린다. **이 설명은 검증하지 않았다**(BGM 레벨을 바꿔 가며 재야 확정된다).
- 내레이션 압축(attack 5 ms, 보상 이득 없음)은 도움이 되지 않았다. 피크는 4.3 dB 줄었는데 음량은 7.2 dB 줄어 PLR이 오히려 커졌다(짧은 어택이 과도음을 통과시킴). 이 실험으로 압축기를 도입할 근거는 얻지 못했고, 코드에도 넣지 않았다.
- 결론: -14 LUFS는 이 조합(드문 짧은 내레이션 + 연속 BGM)에서 리미터 예산 안으로는 도달하지 못한다. 선택지는 목표값 낮추기, 리미터 예산 늘리기(왜곡 위험), BGM 레벨 조정이며 모두 청취로 정해야 한다. 플랫폼별 권장 음량은 확인하지 못했으므로 어떤 값이 맞다고 말하지 않는다.
- 압축 없이 마스터링한 결과와 압축 변형은 CI 아티팩트 `listening_compress/`에 있다.

## 3. CI가 잡아낸 Windows/Kokoro 결함 (모두 수정, 회귀 테스트 추가)

로컬(Linux) 테스트는 전부 통과하던 상태였다.

| # | 결함 | 영향 |
|---|---|---|
| 1 | 자식 프로세스 stdout 기본 인코딩이 cp1252 | 워커가 한글 오류 메시지·IPA 문자에서 죽음. **Windows에서 발음 사전의 IPA 표기가 조용히 깨질 수 있었음** |
| 2 | `ffmpeg -filters` 출력 형식이 FFmpeg 9에서 달라짐 | `doctor`가 모든 필터를 없다고 보고 -> `-h filter=NAME`으로 확인 |
| 3 | misaki가 첫 합성 때 spaCy 모델 설치 출력을 stdout에 씀 | JSON 프로토콜 파손 -> 워커가 프로토콜 채널을 따로 확보하고 부모는 JSON이 아닌 줄을 무시 |
| 4 | `uv pip install`이 상속된 `VIRTUAL_ENV`(메인 환경)에 설치 | 워커 환경에 `VIRTUAL_ENV` 지정 |
| 5 | 워커 사망 직후 다음 호출이 죽은 파이프에 씀(자식 미회수 경쟁 조건) | 사망 감지 즉시 회수·핸들 폐기 |
| 6 | venv의 `python.exe`는 런처라 PID로 잰 메모리가 3.9MB | 워커가 자기 최대 메모리를 보고 (실제 1390MB) |
| 7 | 생성된 Kaggle 스크립트가 한글 `print`에서 cp1252로 죽음 | 스크립트 시작 시 UTF-8 고정 |

## 4. 구현 중 발견·수정한 설계 결함 (로컬)

- 오디오 스트림 `start_time`이 영상과 다른 파일에서 `align`이 엉뚱한 톤을 고름 -> 스트림 시작 시각 차이 반영(원본 소리 추출에도 적용)
- 비트 분석: 지속음 패드를 85 BPM(신뢰도 0.98)으로 오판 -> 3대역 onset과 절대 강도 게이트로 수정. 지속음 패드 위의 약한 박은 대역 분리 후 검출
- 보컬 휴리스틱 임계값은 추측이 아니라 합성 신호에서 측정한 분포로 정함

## 5. 아직 검증되지 않은 것 (정직한 목록)

1. **사용자 PC의 성능**(콜드 스타트·RTF·메모리). 러너 수치로 갈음하지 말 것. `configs/acceptance_wait.yaml`이 비어 있어 통과/실패 판정도 보류 상태
2. **발음·음색·억양** - 산스크리트 카운트(Ekam, Dve ...), 강조 조각 합성의 억양, 속도 0.95의 자연스러움. 청취 필요
3. **Gemini 실제 호출** - `gemini-api` CLI 설치와 키, 음성 이름, 출력 형식, 무료 한도. `ai.google.dev`가 막혀 공식 문서를 읽지 못함
4. **Kaggle 실제 실행** - ACE-Step 설치(uv sync, Python 3.12), T4 호환(bf16), 속도, 무료 한도, 인증. 생성 스크립트는 한 번도 Kaggle에서 돌지 않았다
5. **실제 음악으로 비트/보컬 분석** - 합성 신호로만 보정했다
6. **스피커 녹음 영상으로 `align`** - 합성 믹스로만 검증
7. **burn-in 안전 영역** - `margin_v` 420px는 추측
8. 강제 정렬 도구 평가(후보 미검증)

## 6. 권장 순서

1. CI 아티팩트의 후보 음색 샘플을 들어 음색 3개를 고르고, 카운트 단어 발음을 평가한다(필요하면 `pronunciations`에 `/음소/` 표기 시험).
2. `script.yaml`에 `voice: {provider: kokoro, voice_id: <선택>}` 지정, `approved: true` 후 `avsync guide`로 촬영용 가이드 생성.
3. 사용자 PC에서 `scripts\setup_kokoro.ps1` -> `avsync benchmark tts --provider kokoro --voice <음색> --acceptance configs/acceptance_wait.yaml`.
4. (선택) Gemini: `gemini-api` 설치, 결제 미연결 키, `avsync gemini confirm-free --yes`, `avsync benchmark tts --provider kokoro,gemini --listen`로 같은 6문장 비교.
5. (선택) Kaggle: `bgm remote-plan` -> 곡 2-3개(10-15초)로 시험 `remote-run` -> `remote-status` -> `remote-fetch`.
